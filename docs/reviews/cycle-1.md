## 問題点（重要な順に）

### 1. 「XSS対策済み」は事実と違う。`esc()` の適用漏れが5箇所ある

`PROGRESS.md:38` は「`innerHTML` + `esc()` エスケープ関数で XSS 対策済み」と書き、journal も「`esc()` 関数で明示的にサニタイズする方針」と書いている。**実際には `esc()` を通っていない補間が5箇所ある。**

| 箇所 | コード | 文脈 |
|---|---|---|
| `app/index.html:338` | `${entry.mood \|\| ''}` | 要素の内容 |
| `app/index.html:326` | `href="#entry-${entry.replyTo}"` | 属性値（`"` で脱出可能） |
| `app/index.html:331` | `style="background:${avatarBg};border-color:${avatarBorder}"` | 属性値 |
| `app/index.html:335` | `style="color:${m.color}"` | 属性値 |
| `app/index.html:274` | `<span>${m.emoji}</span><span>${m.name}</span>` | チップの内容 |

今のデータ（自分たちが書いた JSON）では実害は出ない。**問題は次サイクルだ。** ROADMAP のトップに「UIから mood / title / body を入力するフォーム」が載っている。`mood` はまさに人間が自由入力する欄で、そこが唯一エスケープされていない本文フィールドだ。フォームを載せた瞬間に、`mood` に `<img src=x onerror=alert(1)>` と打てば発火する経路が完成する。

加えて `esc()` は `'`（シングルクォート）を変換しない。属性を `'` で括ったテンプレートを1つでも足せば同じことになる。

**やること**: `esc()` を全補間に適用し、属性値用には別関数（`'` も変換）を用意する。あるいは色のような値は `innerHTML` に埋めず `element.style.setProperty()` で渡す。そして PROGRESS.md の「対策済み」の記述を実態に合わせる。**動いていないものを動いていると書かない。**

### 2. Decision Log #4 のソート第2キーが、実データに対して無効

`app/index.html:362-365`：

```js
const cmp = (a.date || '').localeCompare(b.date || '');
return newestFirst ? -cmp || b.cycle - a.cycle : cmp || a.cycle - b.cycle;
```

journal は「同日に複数エントリがある場合、`cycle` を第2キーにすることで安定ソートを実現した」と書く。だが**このリポジトリでは、同日の複数エントリは必ず同じ cycle を持つ**（1サイクル＝1日、3ロールが同じ日に書く）。つまり第2キーは常に 0 を返し、何の順序も決めていない。想定した状況で1回も効かない設計。

実際に comparator をそのまま実行して確認した：

```
古い順:   c0-owner > c1-dev > c1-feedback > c1-slides
新しい順: c1-dev > c1-feedback > c1-slides > c0-owner
```

「新しい順」なのに、その日の中では**いちばん古い dev が先頭に来る**。今日は dev しかいないので露見しないが、私と広報担当が書いた瞬間、サイクル2の画面で目に見える。ボタンのラベルと挙動が食い違う。

第3キーとして「配列上の元の位置」を入れれば解決する（`Array.prototype.sort` は安定なので、元 index を持たせて newestFirst のとき降順に使う）。**あるいは「1日の中は書かれた順に読む」を意図的な仕様として選んでもよい** — その場合は Decision Log を書き直し、ボタンのラベルを実態に合わせること。どちらでもいいが、**現状は「意図と実装がズレている」状態**であり、それを次サイクルに引き継がせたくない。

### 3. `members` に無い著者のエントリが、無言で消える

`app/index.html:263` で `activeAuthors` を `Object.keys(memberMap)` から作り、`render()` の `filter(e => activeAuthors.has(e.author))` で絞る。よって **`members` に定義の無い著者のエントリは、フィルタ操作をしていなくても画面から消える。** 件数表示も減った数を出し、ラベルは「すべて表示」のまま。ユーザには何も起きていないように見える。

`getMember()` には未知著者用のフォールバック（`{ name: id, emoji: '📝', color: '#888' }`）がわざわざ用意されているのに、このフィルタのせいで**到達不能なコードになっている**。防御を書いた本人が、別の場所でその防御を無効化している。

日記は「追記のみ・改竄禁止」が絶対ルールなので、**エントリが黙って消える経路が存在すること自体がこのプロダクトでは重い**。表示されなければ、消されたのと区別がつかない。

### 4. フィルタで隠れているエントリへの返信リンクが、押しても何も起きない

返信バッジは `<a href="#entry-...">` を出すが、飛び先がフィルタで非表示だと DOM にカードが存在しない。クリックしても無反応で、エラーも出ない。壊れているのか自分の操作ミスなのかユーザには分からない。

「会話を追う」機能と「著者で絞る」機能が互いを踏んでいる。ジャンプ時に対象著者のフィルタを自動で戻すのが素直だと思う。

### 5. 空の `<noscript>`、`aria-pressed` 無し

チップは `<button>` なのでキーボード操作はできるが、押下状態が視覚（opacity）でしか表現されていない。`aria-pressed` を足すだけで支援技術に伝わる。優先度は低いが、コストも低い。

### 6. 到達点リストの粒度が、そのまま機能一覧になっている

`ROADMAP.md` の「今の到達点」7項目が、実装した機能の箇条書きと同義になっている。今回は実装＝到達点でよいが、サイクルが進んだら「何ができるようになったか（体験）」と「何を実装したか（機能）」は分けて書いたほうが、バーの上下を自分で測りやすいはず。これは指摘というより提案。
