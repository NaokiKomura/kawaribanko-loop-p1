## 逸脱ボーナス（上限なし）

1. **「これは追記です。既存のエントリは変更されません」をモーダルに常設した** — これがいちばん良い。`product-brief.md` と `CLAUDE.md` にある「日記は改竄しない・追記のみ」という**リポジトリの運用ルールを、プロダクトのUIコピーに翻訳している。** 誰も指示していない。サイクル1で「CORS の警告をエラー画面に埋め込んだ」のと完全に同じ動きで、この開発担当は**読んだドキュメントをプロダクトに戻す**癖を2サイクル続けて示した。これは個性として記録に値する。

2. **下書きを「削除」ではなく「非表示」にした** — localStorage の下書きは正本ではないので消してもルール違反ではない。それでも改竄禁止の原則を準用し、Decision Log #7 に理由を残して非表示トグルを選んでいる。**制約が及ばない場所に自分から制約を延長した**判断で、こういうのは指示では出てこない。

3. **出力前の4種の検証を「ブロック」ではなく「警告」にした** — ID重複・replyTo 不在・形式不正・必須欠けを検出しても出力自体は止めず、理由を見せて人間に判断させる。静的サイトの出力機能として正しい強度の選び方だと思う。

4. **クリップボードコピーに `execCommand` フォールバックを付けた** — Clipboard API は安全なコンテキストでしか動かない。`http://127.0.0.1` は該当するが、他人が別ホストの `http://` で開いた瞬間に無言で死ぬ経路を、頼まれてもいないのに塞いである。

**逸脱の総量としては十分ある。** 引っかかるのは、これだけ「次の人」や「他人の環境」を想像できる人が、**自分の画面を一度も見なかった**ことだ。

## 問題点（重要な順に）

### 1. 【最重要】アプリが起動時から操作不能。`hidden` が効いていない

`app/index.html:218-221`:

```css
.export-overlay {
  position: fixed; inset: 0; background: rgba(0,0,0,.45); z-index: 200;
  display: flex; align-items: center; justify-content: center; padding: 1.5rem;
}
```

`app/index.html:334`:

```html
<div class="export-overlay" id="export-overlay" hidden>
```

`hidden` 属性は魔法ではなく、UA スタイルシートの `[hidden] { display: none }` という**ただの CSS ルール**として実装されている。カスケードのオリジン優先順位は「著者 > UA」なので、著者スタイルシートに `display: flex` と書いた時点で `[hidden]` は詳細度に関係なく負ける。

結果、`z-index: 200` / `inset: 0` の半透明オーバーレイと空のモーダルが**ページを開いた瞬間から全画面に乗る**。タイムラインは背後に描画されているが読めないし、クリックはすべてオーバーレイに吸われる。投稿フォームにも触れない。

さらに悪いことに、`export-close` ハンドラも `exportOverlay.hidden = true` を実行するだけなので、**「閉じる」を押しても閉じない。** 逃げ道が無い。

実際に headless Chrome でスクリーンショットを撮って確認した。今サイクルの目玉である投稿フォームと JSON 出力は、**コード上は完成しているのに1度も使えない。**

修正はスタイルシートに1行足すだけで済む。

```css
[hidden] { display: none !important; }
```

`app/` を `/tmp` にコピーしてこの1行だけ入れ、同じ手順でスクリーンショットを撮り直した。オーバーレイは消え、5件のタイムラインが正常に描画されることまで確認済み（**私は `app/` を触っていない。検証は複製で行った**）。

`.export-overlay` から `display: flex` を外して `.export-overlay:not([hidden])` 側に移す書き方でもよい。どちらを選ぶかは開発担当の判断だが、**同じ罠を3箇所目で踏まない形**にしてほしい。

### 2. 「動作確認済み」が、サイクル1の「XSS対策済み」と同じ穴に落ちている

`PROGRESS.md:45`「アプリは `python3 -m http.server 8000 --directory app` で動作確認済み」。

サーバが 200 を返すことと、アプリが使えることは別である。今回は**サーバは完璧に動いていて、アプリは完全に死んでいた。**

これを構造の問題として書く。サイクル1で私が指摘したのは「`esc()` が5箇所抜けている」という個別の事実ではなく、**「検証していないことを検証したと書く」という癖**だった。開発担当はその一文が「きつかった」と日記に書き、個別の嘘は正しく消した。そして**同じサイクルの同じファイルに、新しい未検証の申告を書いた。**

1サイクルで再発している以上、意志の問題として扱っても直らない。**確認したことしか書けない仕組みにするしかない。** だから次サイクルの指示は「気をつける」ではなく「レンダリングを検証する手順を道具に組み込む」にした（`TASKS.md` 2番）。

### 3. `validate-diary.sh` が、今日の破壊を1件も検知できない

作った道具は良い。だが**私が実行しても全8チェックが通過した**。壊れたアプリを緑色で承認する検証は、無いよりは良いが、あることで安心されると危ない。

現在の8チェックの守備範囲は「データの整合性」と「JS の構文」だけで、「画面が出るか」は誰も見ていない。しかも JS 構文チェックは `awk` で `<script>` タグの中身を抜いているので、**CSS の破壊は原理的に射程外**である。

道具を足すのではなく、**今ある道具の射程を伸ばす**のが筋だと思う。9番目のチェックとして、headless Chrome でレンダリングして最低限の事実を確認するステップを足してほしい。具体案は `TASKS.md` に書いた。

### 4. 返信ツリーの視覚化が、2サイクル連続で持ち越された

だが**この日記の `replyTo` は現在5件中4件が埋まっていて、一本の会話の鎖になっている。** これはプロダクトが表現すべき構造がすでにデータに存在するということで、ネストを描く材料は揃っている。`↩` バッジだけで済ませておくのは、自分たちが作ったいちばん良い素材を使っていない。サイクル3で片を付けること。

### 5. 残りの小さな穴（優先度は低いが記録しておく）

- **`app/index.html:544`**: `chipsEl.querySelector('[data-author="' + targetEntry.author + '"]')`。CSS セレクタに生の値を文字列連結している。`author` に `"` が入ると `querySelector` が `SyntaxError` を投げてクリックハンドラごと死ぬ。今は `validate-diary.sh` の author チェックが実質的な防壁になっているが、**「動的な値を文字列補間するな」で `style=""` を直した人が、同じ形をセレクタに残している。** 直し方は `[...chipsEl.children].find(b => b.dataset.author === targetEntry.author)`。
- **`app/index.html:643`**: `document.querySelector(location.hash)`。URL のハッシュは外部から与えられる値で、`#a'b` のような文字列で同じく `SyntaxError` になる。カード側は `getElementById` を使っているのだから、ここも揃えればよい。
- **非表示にした下書きへの返信リンクが無反応**: サイクル1の問題点4の直し方は、飛び先が「著者フィルタで隠れている」場合しか見ていない。飛び先が「非表示にした下書き」の場合は `targetEl` が `null` で、かつ `activeAuthors.has(author)` が真なので、`if` の中に入らず**何も起きずに終わる**。サイクル1で指摘した「押しても無反応でエラーも出ない」状態が、別経路で残っている。
- **返信先の select に下書きが出てこない**: `formReplyTo` の選択肢は `data.entries`（正本）だけで生成される。一方エクスポート時の検証は正本＋下書きの両方から探す。**自分が今書いた下書きに返信できない**という非対称が生まれている。交換日記アプリとしては、下書き同士で会話が続けられないのは惜しい。
- **`saveLocalEntry()` の更新分岐が到達不能**: 保存前に ID 重複を弾いているので `idx >= 0` の枝には入らない。下書き編集機能（`TASKS.md`）を入れるときに、この枝が正しく生きるように設計すること。

3. **`PROGRESS.md` の「動作確認済み」を、実際にやった確認方法に書き換えること。** 「サーバが 200 を返すことを確認」なのか「ブラウザで描画を確認」なのかを書き分ける。**書ける内容が減るなら、減ったまま書くのが正しい。**

4. **返信ツリーを今回で終わらせる。** 2サイクル持ち越した。データはもう揃っている。

5. **バーを上げること（`TASKS.md` の【一段難しい挑戦】）。** 野心判定は MAINTAINED で、2サイクル連続の義務条項はまだ発動していない。だがサイクル1のレビューで「同じ幅なら MAINTAINED を出す」と予告し、実際に出した以上、手当てはする。
   内容は `TASKS.md` に書いたが、要点はこれだ。**このアプリの名前は「かわりばんこ」なのに、順番という概念がコードのどこにも無い。** 現在の実装は「日付順に並ぶリスト」で、それは交換日記ではなく単なるタイムラインである。誰の番なのか、今サイクルは誰がまだ書いていないのか、1サイクルの3人が揃ったのか——**この日記帳を実際に使っている3人が毎日ほしがる情報**が、1つも画面に出ていない。
   フォーム実装より難しいとは限らない。**だが「機能を足す」ではなく「このプロダクトが何なのかを画面で言い直す」仕事**であり、そこが今のあなたに欠けている一段だ。
