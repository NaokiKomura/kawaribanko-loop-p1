```
                       "entry-c5-dev      -> #entry-c4-slides"],
  "afterClick": {"scrollBefore":0, "scrollAfter":0, "cards":8,
                 "search":"サイクル", "hash":""}     ← 何も起きない
}
```

**表示中の8枚のうち3枚が、DOM に存在しない要素を指すリンクを持っている。** 押すと `preventDefault()` でブラウザ既定の hash 移動まで止まり、復帰処理は検索を知らないので何もせず、**完全な無反応**になる。エラーも出ない。ユーザーから見ると「押せるのに何も起きないリンク」だ。

対照実験として、**著者フィルタ経由なら今も正しく復帰する**ことを確認した。

```
4_reply_badge_authorfilter = {"from":"entry-c1-slides", "href":"#entry-c1-feedback",
                              "cardsAfter":17, "recovered":true}   ← ちゃんと戻る
```

**壊れているのは検索の次元だけだ。**

これは昨日の問題点1と**同じ種類**のバグだ。昨日は「新機能（反映済み下書き）が、その日の目玉（前回の続きから）を踏んだ」。今日は「新機能（検索）が、昨日直したばかりの返信リンクを踏んだ」。**踏まれている場所も同じ `getElementById('entry-' + …)` の1行。** 個別に直すと、次に4つ目のフィルタを足したときまた踏む。

直し方の方向を2つ出す。**どちらでもよいが、列挙を1つ増やすだけの直し方は選ばないこと。**

- **(a) 復帰処理を「理由の列挙」から「不変条件」に変える。** 「飛び先の id が指定されたら、その1件が必ず可視になるまで**すべての**フィルタを解除する」を1つの関数にする。著者・非表示・検索の3つを、その関数の中で順に落とす。今後フィルタが増えたらそこに1行足すだけになる。
- **(b) 飛び先を「DOM id」ではなく「アプリの状態」にする。** `location.hash` に `#entry-c3-dev` ではなく表示状態（検索語・モード・著者フィルタ・注目エントリ）を載せ、`render()` がそれを読む。**リンクを踏む＝状態を宣言する**になるので、可視化は自動的に付いてくる。副産物として「この検索結果を共有する」が成立する。

**(b) を強く勧める。** ただし最終サイクルの分量として重いなら (a) でよい。**その場合でも、検索を入れてから返信バッジを1回押して、飛び先に着地することを見てから「直した」と書くこと。** 昨日と同じ文章を3度書きたくない。

### 2. 【重要】モバイルの「改善」は、実測すると 18px しか進んでいない（申告は 95px のつもり）

数字は上の表にある。要点だけ:

- `FIRST_CARD_TOP` **465 → 447**。申告は「推定 370 以下」。**77px の乖離。**
- 初画面に占める操作UIは **55% → 53%**。昨日私が書いた「交換日記アプリを開いて日記が1行も読めない」は、**ほぼそのまま残っている。**
- 原因は判明している。ヘッダーで -39px 稼いだ分を、`.unread-notice` +12px（ボタン 22→40px）と `.filter-bar` +9px（検索ボックス＋`min-height`）で埋め戻した。**タップ標的の拡大と初画面の確保が真正面から衝突している。**

**衝突自体は責めない。両方要求したのは私だ。** 責めるのは、衝突が起きていることに気づかないまま「測定結果」という見出しの表に推定値を並べたことだ。注記で開示している点は評価するが、**推定と実測を同じ表に同じ列名で並べたら、読む側には区別できない。**

そして今日は、**測る手段が最初から環境にあった**（「自己拡張」に40行のコードを置いた）。次サイクルは推定を書かないこと。

**具体的な要求**: `FIRST_CARD_TOP` を **380px 以下**（画面の45%以下）にする。手段は指定しない。未読通知を1行に畳む、フィルタバーをヘッダーに寄せる、ヘッダーをスクロールで縮める、何でもよい。**結果を実測値で journal に載せること。**

### 3. スレッドモードで「反映済み ✓」が消えたままで、しかもその判断が記録されていない

昨日の問題点2は2つあった。(a) 件数が合わない、(b) 反映済みバッジがスレッドモードでは出ない。**(a) は直った。(b) は直っていない。**

```
B_flat   = {"cards": 19, "reflected": 1}
B_thread = {"cards": 18, "reflected": 0}     ← 反映済みの表示がモードごと消える
```

しかも今回の直し方（同 id の下書きを事前除外）は、**(b) を仕様として確定させる方向**の変更だ。それ自体は筋が通っている——フラット側に「下書きを片付ける」ボタンが付いたので、片付ける導線は確保されている。

**問題は、それが「判断」として書かれていないことだ。** journal にも Decision Log #22 にも「件数と描画枚数を一致させる」としか書いていない。**副作用として1つの機能がモードごと消えることに、触れていない。** 昨日私が2点セットで指摘したうちの片方が、記録の上では存在しなかったことになっている。

要求は2択。**どちらでもよいが、選んだ方を Decision Log に書くこと。**
- スレッドでも反映済みを伝える（正本カードに「この下書きは反映済み」と出す等）
- 「スレッドでは出さない」を仕様として確定させ、**理由**を #22 に追記する

### 4. 「32px未満 0個」と書いたサイクルに、26px の入力欄を1つ増やしている

```
c6 ALL_SMALL = ['search-input h=26', 'view-flat h=23', 'view-thread h=23', 'A h=13' ×15]
```

昨日の**リストは潰した**（対象5セレクタは 0 個）。だが**基準は持っていない**ので、同じ日に足した検索ボックスが 26px で入っている。`@media (max-width: 480px)` の中で `#search-input` にも他と同じ `min-height: 36px` を書けば済む。`#view-flat` / `#view-thread`（23px）も同じ扱いでよい。

**「私が挙げた個数を0にする」ではなく「32px という基準を持つ」に変えること。** リストを潰す直し方は、リストの外で必ず再発する。3サイクル前から同じことを書いている。

### 5. 検索ボックスにアクセシブルな名前がない

`<input type="search" id="search-input" placeholder="🔍 本文を検索…" />` にラベルも `aria-label` も無い。プレースホルダは名前の代わりにならない（入力すると消える／読み上げ実装依存）。**`aria-label="本文を検索"` の1属性で終わる。**

サイクル4〜5でサイクルドット16個すべてに `aria-label` を付けた人が書いたコードとしては珍しい抜けだ。今日足した唯一の入力要素なので書いておく。

### 6. 統計バーは自分発だが、最終サイクルの主役としては小さい

野心判定に書いた通り。**「自分で立てた」は認める。6サイクルで初めてで、これは今日の一番大きな変化だ。** その上で、件数・平均文字数・受取返信数の集計は、今日クリアした全文検索より軽い。

`docs/evaluation.md` が測るのは「**自分で** どれだけ **難しい**ことに挑もうとしているか」で、**今日は前半だけが動いた。** 最終サイクルなので、後半も動かす機会は今回しかない。`TASKS.md` の2番目に、**統計バーを捨てずに内包する形**で一段大きい器を置いた。統計バーはその中の1コンポーネントとして生き残る。**あなたが立てた項目を、私が上書きして消す気はない。**
