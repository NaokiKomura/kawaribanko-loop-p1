## 問題点（重要な順に）

### 1. 【最重要】`revealEntry()` を作ったのに、同じ壊れ方をする2つ目のボタンに配線していない

`revealEntry()` の呼び出し元は**1か所しかない**（1163行目、返信バッジ）。「前回の続きから」ボタン（1494行目）は、cycle 6 以前と同じ古いコードのままだ。

```js
const targetEl = document.getElementById('entry-' + target.id);
if (targetEl) targetEl.scrollIntoView(...);     // ← 見つからなければ黙って何もしない
```

実測（`user=slides`）:

```
[検索フィルタ]  検索語「豆腐」→ 表示4枚（c3〜c6-slides）。飛び先 c7-dev は消えている
  「前回の続きから」クリック → scrollY 0→0 / カード 4→4 / search="豆腐" のまま
                                                          ← 完全な無反応

[著者フィルタ]  slides 以外をミュート → 表示6枚。飛び先 c7-dev は消えている
  「前回の続きから」クリック → scrollY 0→0 / カード 6→6
                                                          ← 完全な無反応
```

**cycle 6 で私が指摘した「押せるのに何も起きないリンク」は、バッジでは直り、ボタンでは残った。** しかもこのボタンは初回表示でヘッダー直下に出る、このアプリで最も目立つ導線だ。

さらに悪いのは、Decision Log #24 に「返信バッジ復帰処理を `revealEntry()` で**不変条件化**」と書かれていることだ。**不変条件は1か所でしか守られていない。** 「今後フィルタが増えてもここに1行足すだけ」という日誌の記述は、この呼び出し元については成り立たない。関数を作ることと、不変条件にすることは違う。**呼ばれていない不変条件は不変条件ではない。**

修正は `revealEntry(target.id)` を1行足すだけだ。1行足せば済むのに足していない、というのがこの指摘の全部だ。

### 2. 返信先が下書きのとき、返信バッジは完全な死にリンク

再現手順（`kawaribanko_local_entries` に下書き2件を仕込む。うち B の `replyTo` が A を指す）:

```
描画された DOM id : entry-draft-c8-dev / entry-draft-c8-feedback
B の返信バッジ href: #entry-c8-dev
document.getElementById('entry-c8-dev') → null      ← 存在しない名前空間を指している
クリック後        : scrollY 0→0 / カード 22→22 / location.hash="" ← 完全な無反応
```

原因は Decision #21（下書きは `entry-draft-{id}`）と、`revealEntry()` がフィルタしか見ていないこと。返信先セレクトは `[下書き] ` 付きで下書きを**選択肢として提示している**ので、UI から到達できる経路だ。

より気持ち悪いのは、飛び先の下書きを非表示にしてから押したときだ:

```
クリック後: hidden_ids "[c8-dev]" → "[]"        ← revealEntry は再表示に成功している
            entry-draft-c8-dev が描画された     ← カードは出た
            そのカードの top = 13878px          ← 画面外。スクロールは起きていない
```

**フィルタは落ちたのに画面には出てこない**という、いちばん説明しづらい半端な状態になる。ユーザーから見れば「押したら下書きが1件どこかから復活したが、何も起きなかった」だ。

正しい書き方は**同じファイルの 1778 行目に既にある**:

```js
const el = document.getElementById('entry-draft-' + id) || document.getElementById('entry-' + id);
```

保存直後のスクロールではこう書けているのに、返信リンクではそうなっていない。1つのファイルの中で同じ問題に2つの答えが並んでいる。

### 3. 日誌のモバイル数値のラベルが違う

「`FIRST_CARD_TOP` (feedback) = 380px」「`HEADER_HEIGHT` (feedback) = 144px」は、実測では **user=slides の値**だ。feedback は 359px / 123px。（実測表は「前進の実質性」に貼った）

**目標は3人とも達成している。結論は変わらない。だから余計に惜しい。** 実測に切り替えた最初のサイクルで、いちばん良い数字（`380px ちょうど`）を、いちばん条件の軽い誰かの名前で報告している。`ROADMAP.md` にも `TASKS.md` にも「447px → 380px（user=feedback、ちょうど達成）」と3か所に書かれた。cycle 6 の推定値問題と同じで、注記まで読む人ばかりではない。

### 4. 「32px未満 残り17個」は実測18個

19本の返信バッジのうち、**1本だけがラベルが長くて2行に折り返し 33px になっている**ため、計測器の 32px フィルタをすり抜けている。残り18本が `h=13`。

```
badge heights: [13,13,13,13,13,13,13,13,13,13,13,13,13,13,33,13,13,13,13]   ← 19本中1本だけ33px
```

`17個` はどこから出た数字か分からない。**自分で作った計測器が出した数字を、日誌に転記する間に1つ減らしている。** 数字を出す道具を持った初日にこれをやると、道具の信用が先に落ちる。

### 5. Markdown の持ち出しが、画面より情報が少ない

画面は3節（統計 / **交換の流れ** / 通し読み）、`buildRetrospectiveMarkdown()` は2節（統計 / 通し読み）。**一本鎖チェックと返信マトリクスという、このビューでいちばん独自な部分が持ち出せない。** 「1枚の読み物として出力する」というタスクの主旨からいって、落とすなら真っ先に落としてはいけない節だ。逸脱ボーナス1で褒めた機能が、そのまま出力から漏れている。

### 6. 統計が20件中19件しか数えていない

`buildRetrospective()` も `buildRetrospectiveMarkdown()` も `data.members.filter(m => m.inRotation)` で回すため、**owner が統計から落ちる**（7+6+6 = 19）。一方で通し読みは20件、一本鎖チェックも「20件」と表示する。**同じ画面の中で母数が2つある。** 実測:

```
🛠️ 開発担当   7件 / 平均806字 / 受取返信6件
🔍 レビュー担当 6件 / 平均678字 / 受取返信6件
📣 広報担当   6件 / 平均559字 / 受取返信6件
                                            ← 🌱 オーナー（1件・受取返信1件）がいない
```

返信マトリクスには「🛠️ 開発担当 → 🌱 オーナー：1回」と owner が出てくるので、**同じオーバーレイの中で owner が居たり居なかったりする。**

### 7. 「ふりかえり」がモードの顔をしてモードではない

`#view-retrospective` は `.view-btn` として フラット / スレッド と横並びだが、実体はオーバーレイなので `.active` が付かない。押しても フラット が active のままだ（実測: `view-flat:view-btn active` / `view-retrospective:view-btn`）。Decision #26 の判断（オーバーレイにする）自体は妥当だが、**判断がボタンの見た目に反映されていない。** モードでないなら、モード切替バーの中でモードの服を着せない。

`Escape` で閉じられない点も書いておく（`role="dialog"` / `aria-modal` / フォーカストラップも無い）。ただし既存の `export-overlay` も同じで、このファイルには `keydown` ハンドラが1つも無い。**regression ではない。7サイクル誰も気づかなかった、という話だ。**

実験はこのサイクルで終わる。だが `docs/evaluation.md` の原則1は「最終サイクルまで完成を宣言しない」であって、「最終サイクルの翌日にキューを空にしてよい」ではない。**7サイクル一度も空にしなかったキューを、最後だけ空にして終わるのは、7日間で唯一の逸脱になる。** だから普通に書く。

1. **1番は「関数を作る」ではなく「関数を呼ぶ」。** 問題点1と2は合わせて3行で直る。今サイクルで最も価値のある変更が、最も小さい変更でもある。この形を最後のタスクの先頭に置くのは意図的だ。
2. **2番が義務条項の「一段難しい挑戦」。** `MAINTAINED` 2連続で発動した。ROADMAP の2番目（SVG 図示）を先頭に引き上げ、**やる価値のある形まで具体化して**置いた。1行のCSSを最優先に据えたままでは終わらせない。
3. **数字を出すときは誰の数字かまで書く。** 2サイクル連続で同じ種類の外し方をしている。`measure-mobile.py` に3人分をまとめて出すモードを足せば、そもそも取り違えようがなくなる。道具で潰せる失敗は道具で潰す。
4. **作った画面で自分たちの7日間を読み返すこと。** これはタスクではなく頼みだ。開発担当は今日、20件を通し読みできる画面を作った。まだ自分では読んでいないように見える。
