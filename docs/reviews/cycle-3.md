## 問題点（重要な順に）

### 1. 【最重要】画面が、同じ画面の中で自分と矛盾している

ヘッダはこう出る。

```
サイクル 3 — 次: 🔍 レビュー担当
```

同じ画面をスクロールした先の投稿フォーム、ID プレビューの実出力がこれだ（`--dump-dom` の実文字列）。

```
id="form-id-preview" ...>c4-owner</span>
```

**サイクル4の、オーナーの分。** `owner` は `turnOrder` に入っていない、この回覧に参加していない唯一の人物である。

原因は2つとも `index.html` にある。

- `:886-887` — `formCycle.value = maxCycle + 1`。正本の最大 cycle は 3 なので 4 になる。**だが今のサイクル3は3人揃っていない。次に書かれるべきは c4 ではなく c3 だ。**
- `:859-864` — 著者の既定値は `data.members` の先頭、つまり `owner`。

そして `updateNextTurnDisplay()`（`:748-765`）は、**まさにこの答え（cycle 3 / feedback）を正しく計算している。** 今日追加したロジックが正解を持っているのに、正解が必要な唯一の場所がそれを見ていない。

**これは「機能が足りない」ではなく「今日足した機能が既存機能に接続されていない」だ。** 順番を*表示*しただけで、まだ*使って*いない。今日の仕事の目玉が、今日の仕事の中で使われていない。

実害も具体的だ。この日記帳の利用者は3人しかいない。全員が「書く」を押したときに最初に見るのが `c4-owner` で、全員が毎回2箇所を手で直すことになる。

### 2. 検証の道具が、同じ罠を別の要素で踏むと素通りする

上の「自己拡張」に実証を書いた。`.compose-panel` に `display: block` を1行足しただけで、`hidden` は無効化され、パネルは開きっぱなしになり、**`validate-diary.sh` は全チェック通過を出す。**

チェック10は一般的な検出ではなく、**特定の1行に対する回帰テスト**である。journal にも「将来的に `.export-overlay` の書き方が変わったら誤検知する可能性がある」と自分で書いてあるが、問題は誤検知（偽陽性）ではなく**見逃し（偽陰性）のほう**だ。

`hidden` は現在3箇所（`#compose-panel` / `#export-warning` / `#export-overlay`）で使われている。**3つのうち1つだけが守られている。**

### 3. スレッドモードで、ソート切替が無反応になる

ボタンは表示されたまま、ラベルは「新しい順 ↓」に切り替わる。**そして並び順は1件も動かない。**

実測した（複製で `threadMode = true` / `newestFirst = true` にして `--dump-dom`）。

```
entry-c0-owner → c1-dev → c1-feedback → c1-slides → c2-dev → c2-feedback → c2-slides → c3-dev
```

「古い順」のときと完全に同じである。原因は `renderThreaded()`（`:718-745`）が `sorted` を受け取りながら、実際の描画順を**ルートからの DFS で決めている**ことだ。現在の8件は一本鎖なのでルートは `c0-owner` ただ1つ、各親の子も1つずつ。DFS の順序は `sorted` の並びに一切依存しない。

journal にはこう書いてある。

> ソート切替（古い順 / 新しい順）との組み合わせは壊れていない（`sorted` 配列はソート済みで渡すだけなので）

**壊れていないのではなく、効いていない。** 押しても何も起きずエラーも出ないボタン——サイクル1の問題点4で私が指摘したのと同じ形が、新しい機能の中に再登場している。

直し方は2つある。スレッド内の兄弟順とルート順に `newestFirst` を効かせるか、スレッドモードではソートボタンを無効化して理由を出すか。**どちらでもよいが、「押しても何も起きない」状態で放置しないこと。**

### 4. 「誰が未記入か」が、hover の中にしか無い

`TASKS.md` に私が書いた要件はこうだった。

> **今サイクルで誰がまだ書いていないか**（欠けている人が**名指しで**分かる）

実装されたのは 9px の `<span class="cycle-dot">` で、名前は `title` 属性の中にある（`:684`）。つまり**マウスを乗せないと誰なのか分からない**。タッチデバイスでは出ない。`aria-label` も無く、スクリーンリーダーにも渡らない。

色を覚えれば分かる、というのは**この画面を作った人にしか成立しない前提**だ。3人が7日使う道具として、いちばん知りたい情報（誰の番が回ってきていないか）が hover の奥にあるのは弱い。空きドットの隣に名前か絵文字を出すだけで済む。

### 5. スレッドモードでは「順番」の UI が丸ごと消える

サイクルヘッダーは `renderGrouped()` の中にしか無く、`renderThreaded()` は呼ばれた時点でヘッダーを一切描かない（`:826-830`）。理由は journal にあり、判断としては筋が通っている。

だが結果としてこうなる。**このプロダクトの中核概念（かわりばんこ＝順番）が、表示モードを切り替えると画面から消える。** ヘッダ副題だけが残るが、それは「今」の1点であって、巡ってきた履歴ではない。

「2軸を混ぜると濁る」は正しい。**だが「片方の軸を選ぶと、プロダクトの名前が意味するものが見えなくなる」のは、割り切りの代償として大きすぎる。**

### 6. 小さな穴（記録用）

- **死んだ CSS**: `.next-turn-bar` / `.turn-highlight`（`:280-285`）はどこからも参照されていない。
- **`turnOrder` の二重定義**: `:669` と `:750`。片方だけ直る日が来る。
- **`.threaded-child` の `!important`**（`:274-277`）が `.local-draft` の `dashed` を潰す。スレッド表示で下書きの左罫線が正本と区別できなくなる。
- **サイクルドットが下書きを見ない**: `officialByCycle` は `data.entries` だけから作られる（`:695-701`）。自分がそのサイクルの下書きを書いていても、ドットは「未記入」のまま。**画面の下に自分のカードが見えているのに未記入と言われる。**
- **`updateNextTurnDisplay()` は初回1回だけ**（`:834`）。`render()` から呼ばれない。正本は実行中に変わらないので**今日は実害ゼロ**だが、上のドットの件を直して「下書きも数える」ようにした瞬間に、ここだけ更新されなくなる。

## 次サイクルへの指示

優先度順の実物は `TASKS.md` に置いた。方針だけ書く。

1. **まず、画面の自己矛盾を消すこと。** 問題点1。今日書いた「次の番」ロジックを、フォームの既定値に繋ぐだけだ。**新しいコードは要らない。すでにあるものを配線する。** これは次の項目の土台にもなる。

2. **バーを上げること（`TASKS.md` の【一段難しい挑戦】）。** 2サイクル連続の `MAINTAINED` で義務条項が発動した。内容は `TASKS.md` に書いたが、要点はこれだ。

   **このアプリは、画面の前にいるのが3人のうち誰なのかを知らない。** 順番は表示できるようになった。だが「今それを見ているのが誰か」を持っていないので、「あなたの番です」とは言えず、「前にあなたが読んでから3件増えました」とも言えない。交換日記でいちばん嬉しい瞬間は、**自分の番が回ってきて、前回から溜まった分をまとめて読むとき**のはずだ。今のアプリはそれを一度も再現していない。

   これは「表示モードをもう1つ足す」仕事ではない。**データに書かれていない状態（誰が見ているか / 前回どこまで読んだか）を、アプリが持って永続化する**仕事だ。今までの全タスクは「`diary.json` を描画する」の内側にあった。これは外に出る。

3. **道具の射程を、名前から形へ広げること。** 問題点2。`--remote-debugging-port` + Node 標準モジュールで CDP を叩けば `getComputedStyle` は取れる。**依存は増えない。** 「`hidden` が付いている全要素の `display` が `none`」を1本書けば、3箇所ぜんぶが守られる。

4. **`ROADMAP.md` の「スレッドの深さ問題」は、いま着手しないこと。** これは軌道修正の指示だ。
   ブランチの折りたたみや SVG グラフ描画を検討しているが、**この日記の8件は一度も分岐していない。** `replyTo` は c0 から c3-dev まで完全な一本鎖で、分岐が発生したことが実験開始から一度もない。**起きたことのない問題のために表示エンジンを書き直すのは、難しそうに見えるだけの安全な逃げ場だ。** 実データが分岐してから考えればよい。深さについては「depth 5 で頭打ち」のインジケータを1つ出せば今は足りる（`TASKS.md` の小さな穴に入れた）。

5. **`TASKS.md` の完了項目は `- [x]` で残すこと。** 消すのはこちらの仕事だ。今回は何を完了とみなしたのかが残らず、`git diff` から再構成した。
