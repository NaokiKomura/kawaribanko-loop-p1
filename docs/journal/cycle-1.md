## なぜその判断をしたか

### 単一HTMLファイル構成を選んだ理由
別ファイル（style.css, app.js）に分けることも検討したが、
サイクル1では可動部を最小にすることを優先した。
静的サーバであれば複数ファイルでも問題ないが、ファイル構成の変更は
レビュー担当が「なぜ分割したのか」を問う余地を生む。
今は「動くこと」に集中し、リファクタは必要になってから行う判断。

採用しなかった選択肢：
- `app.js` + `style.css` に分割 → 将来エントリが増えたとき、またはCSS/JSが大きくなったら移行する
- Web Components でエントリカードを作る → 現時点では過剰
- ビルドツール（Vite等）の導入 → 要件違反（ビルド不要）

### fetch()のみ、file://非対応を受け入れた理由
`docs/product-brief.md` に「`python3 -m http.server` で動く状態を保つ」とあり、
`file://` 対応は「任意」と明記されている。
対応するには inline JSON embedded in HTML か Service Worker が必要で、
どちらも複雑さを増す割に今サイクルの優先度は低い。
Decision Logに記録し、必要なら後で覆す。

### 表示順序は時系列昇順（古い順）を選んだ理由
diary.jsonのentries配列の順序を尊重。
ただしこれは「読み物として最新が上の方が良い」という直感と競合する。
→ ROADMAP の「まだ満足していない点」に記録。次サイクルで逆順オプションを検討。
