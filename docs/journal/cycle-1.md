# 開発日誌 — サイクル 1

**日付**: 2026-08-07  
**担当**: dev

## 今回やったこと

プレースホルダのHTMLのみだった `app/index.html` を、実際に動く交換日記アプリに作り替えた。

### 実装した機能

- `fetch('data/diary.json')` で日記データを取得して全エントリを表示
- 著者ごとに色（members[].color）・絵文字・名前で視覚的に区別
- ヘッダのメンバーチップボタンで著者をフィルタリング（最低1人は常に表示）
- 古い順/新しい順のソート切替
- `replyTo` フィールドがある場合、返信先エントリへのジャンプリンクを表示
- エラー時にCORS問題とサーバ起動コマンドを説明するメッセージ
- スクロール後 `location.hash` があれば該当エントリへスムーズスクロール

---

## なぜその判断をしたか

### 外部ライブラリなし

制約（「依存パッケージは原則ゼロ」）に従ったことに加え、バニラJSで十分な複雑度だったため。
React/Vueなどを入れても機能的なメリットが出ない段階で導入すると後のサイクルで縛りになる。

### `fetch` ベースのデータ取得

`file://` プロトコルでは `fetch()` がCORSエラーになるが、CLAUDE.mdに「静的サーバ前提」と明記されているため、
その方針に従った。むしろ `file://` での動作を試みると読み込みのインラインJSON埋め込みなど設計が複雑になる。
エラーメッセージで原因をユーザに伝えることで対処した。

### 著者フィルタの「最後の1つは外せない」制約

全著者を非表示にすると何も表示されない状態になり、ユーザが戸惑う。
実装コストは低く（`activeAuthors.size === 1` のガード1行）、体験が明確に良くなるため採用。

### XSS対策（`esc()` 関数）

日記の本文にはユーザが任意のテキストを書く想定。`innerHTML` を使う場合はエスケープが必須。
`textContent` に逃げるとホワイトスペース制御が難しくなるため、`esc()` 関数で明示的にサニタイズする方針にした。

---

## 詰まった点と解決

### CORSの罠

実装前に「fetchがfile://で失敗する」という既知の問題を認識していたため、
設計段階でサーバ前提と決めた。罠に落ちなかったのはCLAUDE.mdの警告のおかげ。

### ソートキーの安定性

`entry.date` でソートすると、同日に複数エントリがある場合の順序が不定になる。
`cycle` を第2キーにすることで安定ソートを実現した。

---

## 採用しなかった選択肢

| 選択肢 | 却下理由 |
|---|---|
| JSONデータをHTMLにインライン埋め込み | diary.jsonが唯一の正本という制約と相性が悪い |
| Shadow DOM / Web Components | この規模では過剰。バニラJSで十分 |
| `localStorage` で diary.json を丸ごとコピー | データの二重管理が生まれる。書き込み機能は次サイクル以降に設計する |
